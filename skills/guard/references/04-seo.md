# SEO & Indexability

Read when the project has public pages. Goal: make the content that matters crawlable, renderable,
indexable where intended, canonically correct and semantically understandable — nothing more.

Ranking is decided by search systems. SEO work improves **eligibility and understanding**. Never claim a
tag guarantees a ranking.

Order of work: **crawlable → renderable → indexable → canonical → understandable → fast.** A page that
cannot be crawled gains nothing from perfect metadata.

---

## 1. Route inventory

For every public route decide, deliberately, four things: **index or not · canonical URL · title/description
source · sitemap or not.**

| Route type | Index | Canonical | Sitemap |
|---|---|---|---|
| Home, category, product, article, service, public profile | Yes | Self | Yes |
| Paginated page 2+ | Usually yes | Self | Usually no |
| Filter/facet combination | Only if it has standalone search demand | Self or parent | Only if indexed |
| Internal search results | No | — | No |
| Cart, checkout, account, dashboard, admin | No | — | No |
| Preview, staging, draft | No + access control | — | No |

Anything private is protected by **authorization**, never by `robots.txt` or a canonical tag.

---

## 2. Crawlability

- `robots.txt` reachable, valid, not blocking CSS/JS needed to render, not blocking anything that must be crawled to see its `noindex`. It lists the sitemap. It is a crawl directive, not access control.
- Important content is reachable through real crawlable links (`<a href>`), not only through a click handler or an infinite scroll with no URL.
- No crawl traps: calendar infinity, unbounded parameter combinations, session IDs in URLs, faceted explosion.
- `X-Robots-Tag` for non-HTML resources (PDFs, generated documents) when they should be excluded.

---

## 3. Rendering

Verify the **rendered HTML**, never the source assumption. For an SEO-critical page, the primary content,
title, canonical and structured data must be present in the server response or reliably rendered.

Choose the rendering model per page type, not for the whole app: static for stable marketing content,
server-rendered or incrementally regenerated for catalogue/content pages, client-rendered for private app
screens. Never convert an entire application to SSR because one public page needs SEO.

Nonexistent routes must return a real 404, not a 200 with an empty shell (soft 404).

---

## 4. URLs, status codes, canonicals

- One host policy (www or not), one protocol (HTTPS), one trailing-slash policy — enforced in the router, internal links, canonicals, sitemap, Open Graph and redirects.
- URLs: stable, readable, lowercase, hyphenated, slug over opaque ID, no tracking or session parameters in the canonical.
- One direct redirect to the final URL. No chains, no loops, no mass-redirecting unrelated old URLs to the homepage.
- Status codes mean what they say: 200 for real pages, 301/308 for permanent moves, 404 for missing, 410 for intentionally gone, 401/403 for protected.
- Canonical: absolute, HTTPS, preferred host, matching the intended URL, not pointing at a 404, not conflicting with a redirect, not pointing across languages. Self-referencing for ordinary unique pages. It is a hint, not a command.
- Deleted content: redirect if a genuine replacement exists, else 404/410 — and remove it from the sitemap and internal links.

---

## 5. Sitemap

Contains the URLs you want discovered: canonical, absolute, HTTPS, 200, indexable. It excludes noindex
pages, redirects, 404s, duplicates, login, internal search and parameter noise. It updates when content
is created, updated, deleted or redirected. `lastmod` reflects a real modification or is omitted. Split
by type for large sites. Never let a private or dashboard URL into it.

---

## 6. On-page

- One useful, unique, descriptive `<title>` per indexable page, in the page's language. No stuffing, no repetition, no invented superlatives.
- A meta description that summarizes the page honestly. The search engine may write its own snippet from the content — which is why the visible content has to be good.
- One clear primary heading, then a real semantic hierarchy. Headings are structure, not styling.
- Content must satisfy the search intent of the page type: a product page is not an article; a category page is not a wall of keyword text.
- Internal links: every important page reachable, descriptive anchor text, breadcrumbs matching the real hierarchy, no orphans, no footer link farms.
- Images: descriptive filenames, alt text that describes the image (not a keyword list, empty for decorative), dimensions set, responsive sources, appropriate loading priority.

---

## 7. Structured data

JSON-LD, generated by the application from real data, describing content the user can actually see.

- Valid JSON, correct type, correct properties, values matching the visible page.
- Never invent GTIN, SKU, prices, availability, authors, dates, ratings or reviews.
- Only the types the page genuinely represents. Adding every schema type is not a strategy.
- Escape and serialize untrusted values properly — JSON-LD is an injection sink like any other output context.
- Eligibility for a rich result is not a guarantee of one. Verify current documentation before shipping a feature-specific schema.

Commonly correct: `Organization` and `WebSite` site-wide, `BreadcrumbList` on hierarchical pages,
`Product` + `Offer` on product pages, `Article` on articles, `Course` on public course pages.

---

## 8. International & RTL

- `lang` and `dir` match the page's primary content.
- Reciprocal `hreflang` annotations with valid codes, plus `x-default` where relevant.
- Each localized page is genuinely localized — not the same page with a translated title.
- Do not canonicalize all language versions to one language. Do not use `hreflang` to paper over unrelated duplication.
- Arabic metadata is written in Arabic, naturally, not machine-translated to fill a tag.

See `07-i18n-rtl.md` for the rendering side.

---

## 9. Security and caching boundaries (non-negotiable)

- Private or authenticated content never becomes indexable to improve SEO.
- SSR/SSG/ISR/CDN caches: a shared cached response contains only public data. Authentication state must not silently change a shared response. Vary or isolate by every dimension that changes output.
- User-generated content is an injection surface for titles, descriptions, canonicals, Open Graph, JSON-LD, sitemaps and redirects. Treat it as untrusted.
- Preview and draft content is access-controlled and non-indexable.
- Staging environments are protected by authentication or network rules, not by `robots.txt` alone.
- Open redirects become SEO abuse — validate redirect targets.

---

## 10. Programmatic pages

Generating pages from data is legitimate only with a quality gate: each page must have unique purpose,
unique useful content, an accurate entity, real search demand and valid metadata. No doorway pages, no
scaled near-duplicates, no cloaking, no hidden text, no fake structured data. If a tactic exists to
manipulate a ranking rather than help a user, reject it.

---

## 11. Subdomains and new projects

A subdomain is treated as its own site: it needs its own verification in Search Console, its own sitemap,
its own robots policy, its own internal linking, and links from the main site where genuinely relevant.
Nothing is inherited automatically.

For a brand-new project the realistic order is: correct technical foundation → genuinely useful content →
internal linking → submission and monitoring → iteration on real query data. Indexing takes time; promise
correctness and eligibility, never a position.

---

## 12. Validation per route

```
status · final URL · canonical · title · description · robots state · h1 · lang/dir
hreflang · OG title/description/image · JSON-LD parses and validates
primary content present in rendered HTML · in sitemap? · no private data exposed
```

Automate the cheap ones in CI: missing/duplicate titles, broken canonicals, noindex-in-sitemap conflicts,
invalid JSON-LD, internal links to 404s, HTTP URLs in canonicals. Fail the build only on what genuinely
justifies blocking a release; warn on the rest.
