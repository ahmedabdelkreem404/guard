# DashboardGuard Skill

## Purpose

DashboardGuard is a reusable, project-agnostic **Administrative Control Plane, CMS, Localization, Permissions, Content, SEO, Media, Payments, System Health, Reporting, Maintenance, Production-Safety, and Dashboard UX** skill.

It is designed to work with:

- `ProjectGuard.md` — security, testing, architecture, performance, reliability, data integrity, production safety
- `SEOGuard.md` — technical SEO, indexability, metadata, canonicalization, sitemap, structured data, public rendering
- `InsightGuard.md` — analytics, behavior tracking, search intelligence, personalization, recommendations
- `DesignGuard.md` — visual identity, UI/UX, responsive/adaptive design, accessibility, motion, frontend organization

Use this skill for dashboards/control panels for any relevant:

- SaaS
- ERP
- CRM
- HRM
- E-commerce
- Education/LMS
- Marketplace
- CMS
- Booking/reservation platform
- Restaurant/ordering platform
- Inventory platform
- Finance/admin platform
- Membership/subscription platform
- Media/content platform
- Mobile application administration
- Web application administration
- Multi-tenant platform
- Internal operations system

The objective is to create a dashboard that gives authorized operators **complete, clear, safe, multilingual, maintainable, performant control over the actual product**, without turning the dashboard into a code editor or an unnecessarily complicated second application.

---

# 0. Activation Rule

DashboardGuard is activated only when explicitly invoked or when a project explicitly requires a dashboard/control-center audit or implementation.

The existence of this file does not authorize automatic implementation of every capability in it.

When active:

1. Inspect the existing dashboard first.
2. Inspect the actual product and business model.
3. Map existing roles, permissions, data, configuration, content, integrations, and operational responsibilities.
4. Determine what is applicable.
5. Reuse existing architecture.
6. Implement only justified capabilities.
7. Validate security, production safety, UX, performance, and cross-skill interactions.

Never rebuild a working dashboard from scratch merely because a different architecture looks cleaner.

---

# 1. Operating Principles

1. The dashboard is a **control plane**, not a code editor.
2. Administrators configure business outcomes through safe structured controls.
3. Normal dashboard workflows must not require HTML, CSS, JavaScript, JSON, raw SQL, raw SVG, or programming code.
4. Normal visual configuration must not require raw hexadecimal color values.
5. Security is always enforced server-side.
6. UI hiding is not authorization.
7. Every high-impact mutation must be deliberate and auditable.
8. Tenant boundaries must remain intact.
9. Historical business facts must not be rewritten accidentally.
10. Production users and data must be protected during changes.
11. Large data sets must be paginated, filtered, virtualized, aggregated, or otherwise bounded.
12. Printing means real printable content, never a screenshot of a page.
13. Languages and translations are first-class data, not scattered hardcoded strings.
14. Media management must be usable without code.
15. SEO management must be structured and generated by the application.
16. Payment controls exist only when payments exist.
17. Offline/manual payment methods exist only where the project's business model and payment flow support them.
18. Health, logs, audit records, and analytics are distinct concerns even when surfaced in one dashboard.
19. Reuse existing ProjectGuard, SEOGuard, InsightGuard, and DesignGuard infrastructure.
20. Avoid over-view, over-flow, over-write, over-engineering, over-configuration, and unnecessary abstraction.
21. Prefer the simplest safe solution that satisfies the real product requirements.

# 3. Dashboard Information Architecture

Avoid a giant flat sidebar.

Use meaningful groups such as:

```text
Overview
├── Users
├── Content
├── Commerce
├── Analytics
├── Marketing
├── SEO
├── Operations
└── Settings
```

Adapt names to the project's vocabulary.

Do not create a 40-item sidebar when grouping can make the system clearer.

# 4. Overview / Command Center

The dashboard home must answer:

1. Is the system healthy?
2. Is anything broken or urgent?
3. What needs action?
4. What are the important business numbers?
5. What changed recently?

Possible content:

- system health
- pending approvals
- active users
- orders
- revenue
- subscriptions
- low inventory
- failed jobs
- recent errors
- search health
- SEO health
- storage status

Only surface metrics that help operators make decisions.

For financial and business-critical values, use authoritative server/database truth.

# 8. Printing — Mandatory Rule

Whenever a dashboard feature offers printing, print the **actual structured information**.

Never implement print as:

```text
Screenshot → printer
```

This rule applies to:

- invoices
- orders
- receipts
- reports
- tables
- user lists
- product lists
- certificates
- statements
- operational reports

The printable representation must contain real text/data and appropriate layout.

---

# 9. Thermal / 80mm Printing

If the product supports thermal printers:

- create a dedicated semantic print layout
- target the actual paper width
- preserve readable text hierarchy
- include required totals/details
- support monochrome printing where appropriate

Do not take a desktop page screenshot and scale it to thermal paper.

# 17. Dangerous Actions

Treat these as high-risk:

- tenant deletion
- permanent data deletion
- backup restore
- payment configuration changes
- domain changes
- authentication configuration changes
- secret rotation
- maintenance mode
- destructive migrations
- disabling critical services

Use stronger protection where justified:

- confirmation
- explicit impact statement
- re-authentication
- MFA
- typed confirmation
- audit log

Do not make every setting require MFA; apply friction proportionally to risk.

# 22. Language Direction

Support:

- LTR
- RTL

The dashboard and product should adapt appropriately.

Arabic generally uses RTL, but do not force RTL based on assumptions for other languages.

---

# 23. Default Language

Maintain a deliberate default language.

Changing it is a meaningful global configuration change and should be audited where appropriate.

---

# 24. User Language Preference

A reasonable precedence is:

```text
Explicit user choice
→ persisted account preference
→ relevant locale hint
→ application default
```

Do not unexpectedly replace an explicit user selection with IP/browser detection.

# 25. Translation Management

When more than one language is enabled, translatable entities should expose language-specific fields.

Example:


---

# 26. No Translation JSON

Normal content editors must not need to enter:

- JSON
- translation objects
- source-code strings
- locale files

The application should persist the structured translations behind the scenes.

---

# 27. Translation Completeness

Show completion state where useful:

```text
Arabic ✓
English ✓
French !
```

Make incomplete required translations easy to find.

---

# 28. Translation Fallback

Use a deterministic fallback policy.

Example:

```text
Requested language
→ default language
→ unavailable state
```

Never render raw translation keys to ordinary users.

---

# 29. Disable Language vs Delete

Disabling a language should normally not destroy its stored translations.

Prefer:

```text
Disable
```

before permanent deletion where practical.

# 205. Golden Rules

1. The dashboard is a control plane.
2. Configure outcomes, not source code.
3. No normal dashboard workflow requires code.
4. No normal dashboard workflow requires JSON.
5. No normal visual workflow requires raw hex colors.
6. Server-side authorization is mandatory.
7. View/Edit/Delete must be permission-aware.
8. Super admin does not mean security can be skipped.
9. Protect tenant boundaries.
10. Audit important administrative actions.
11. Preserve historical business facts.
12. Prefer reversible actions when appropriate.
13. Languages and translations are structured data.
14. Arabic/English must work when required.
15. Additional languages should be addable where supported.
16. Translation forms adapt to enabled languages.
17. Media management must not require code.
18. Upload, replace, remove, and safe URL workflows should be available where relevant.
19. Hero media should support real product needs, not arbitrary complexity.
20. SEO is configured through structured fields.
21. The application generates the technical SEO output.
22. Never invent schema, reviews, ratings, prices, or identifiers.
23. Payment modules appear only when payments exist.
24. Offline payment methods appear only when supported by the real business flow.
25. A payment screenshot/proof is a claim until verified.
26. Health, logs, and audit are related but distinct.
27. Reports use authoritative data.
28. Printing prints real structured data.
29. Thermal printing gets a dedicated layout when supported.
30. Maintenance must respect architecture and customer continuity.
31. V1/V2 is a migration strategy, not a fashion statement.
32. Production data must be protected during updates.
33. Use safe migrations and recovery strategies.
34. Reuse existing architecture.
35. Reuse shared functions/components.
36. Use meaningful file names.
37. Do not name files after people or brands.
38. Keep the dashboard visually aligned with the product.
39. Do not clone competitors.
40. Do not imitate distinctive WhatsApp-like motion or branded interaction language.
41. Keep animation purposeful.
42. Support reduced motion.
43. Support tiny screens through 4K.
44. Do not allow accidental overflow.
45. Paginate large data.
46. Avoid giant initial payloads.
47. Avoid excessive polling.
48. Avoid unnecessary real-time architecture.
49. Avoid custom platforms unless the product actually needs them.
50. Use simple structured controls instead of code editors.
51. If SEO changes, run SEOGuard.
52. If security/permissions change, run ProjectGuard.
53. If analytics/recommendations change, run InsightGuard.
54. If visual/UI behavior changes, run DesignGuard.
55. Never silently skip a relevant category.
56. Never claim a feature passed testing unless it was actually validated.
57. Fix root causes.
58. Preserve working behavior.
59. Stop when the simplest safe solution is good enough.
